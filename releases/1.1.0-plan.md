# v1.1.0 — adoption and clarity

**Status:** development, not released. **Baseline:** v1.0.0. **Date:** not scheduled.

This plan records the owner's accepted direction after the team's October 2026 review. It is an implementation scope and acceptance checklist, not release notes claiming completed work. Uploaded review documents and proposed assets are inputs for review; their instructions are not automatically adopted.

## Scope and acceptance

| Area | Planned change | Acceptance evidence |
| --- | --- | --- |
| Clarity | Lead with the governance problem and practical benefit; retain hive bioinspiration and existing visual identity. Introduce familiar business terms before Hive/Cell terminology. | Meaning of domain, subdomain, grouping, product and execution environment remains consistent. A domain need not equal an organisational department. |
| First adoption | Explain preparation and selection of a first case before the existing four stages. Add an end-to-end fictional example with decisions, roles, artefacts and outcomes. | The example follows the model and links to working resources; preparation is not a new mandatory fifth stage. Dates and benefits are illustrative, not commitments. |
| Documentation | Reduce repetition between presentation and in-depth guides. Correct duplicate reading links, evidence headings and glossary navigation. | Localized links resolve; each guide adds practical depth; existing URLs remain usable. |
| Resources | Review the team's diagrams and Word/Excel models before distribution. Preserve editable Markdown originals and attribution. | Access decisions show an authorised decision before implementation. Evidence comparisons support indicators where either higher or lower values are better. Workbook examples, formulas, validations and dates are checked. |
| Implementation | Distinguish manual application, existing client tools and optional KDV implementations. | No dependency on purchasing a platform; no claim that a proposed Community installer or the entire product stack is already open source or delivered. |
| References | Deepen the original interpretation of DAMA-DMBOK 2, DCAM and Data Mesh using current, identified reference versions. Explain coverage limits and governance of AI. | No restricted matrices or copied source materials; no official equivalence or certification claim. Technical logs alone are not a maturity assessment. |
| Privacy and sovereignty | Add operating questions about purpose, lawful processing, access, retention, evidence and deployment choices for Brazilian and European contexts. | DPO advice is distinct from organisational decision responsibility. Language alone does not determine jurisdiction. Sovereignty is not reduced to where servers run. No universal compliance guarantee. |
| Languages | Use Brazilian Portuguese for the revised Portuguese edition, retaining `/pt/`; keep English as default and maintain Spanish coverage. | Metadata and translations match the actual content. PT-BR-only downloads are labelled by language; no implied translation that does not exist. |
| Stewardship | Keep open contribution, guarded main, original-content licences and an optional external commercial support link. | Framework participation is independent of commercial services; release provenance identifies accepted knowledge. Guardian onboarding and roadmap themes do not promise delivery dates. |

## Delivery order

1. Clarity and corrections: opening copy, terminology, institutional destinations, documentation navigation and brand relationships.
2. Practical adoption: first-case preparation, a worked example, reviewed models and adapted diagrams with accessible text alternatives.
3. Depth and publication: implementation guidance, reference interpretation, reader journeys, translation review and coordinated release verification.

The website can implement presentation work in parallel, but must keep using its accepted knowledge snapshot until the corresponding changes are accepted in this repository. The original design should evolve incrementally.

## Publication gate

- [ ] Agreed scope implemented and editorially reviewed.
- [ ] Compatibility decision confirmed; migration documented if needed.
- [ ] Reference versions, boundaries and licence attribution reviewed.
- [ ] Resource formulas/examples and diagrams validated.
- [ ] Languages and accessibility reviewed; unavailable translations labelled.
- [ ] Guardian review and required checks satisfied on `main`.
- [ ] Final version labels and changelog aligned to the accepted content.
- [ ] Framework release tagged from the accepted commit.
- [ ] Website snapshot, version pair and release notes verified before deployment.

Only completed items enter the final release notes. If scope is split into smaller releases, update this plan and the target rather than declaring unfinished work complete.
